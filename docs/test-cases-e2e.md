## 1. 前提事項

- 実行: `npm run test:e2e`（Playwright）。事前にローカルSupabaseを起動しておく（README参照）。**本番には接続しない。**
- ブラウザ: Chromium
- プロジェクト（`playwright.config.ts`）:
  - `app`: 開発サーバー（`http://localhost:5173`）に対する機能テスト。`pwa.spec.ts` 以外のすべて
  - `pwa`: 本番ビルド（`dist-e2e/`）を `vite preview`（`http://localhost:4173`）で配信し、Service Worker・オフライン・CSPを検証。`pwa.spec.ts` のみ
- テストごとに新しいユーザーを管理APIで作成し（secret keyはテストコード内のみ。アプリ・リポジトリには入れない）、ログイン済みのセッションを localStorage に注入して開始する。テスト同士のデータは分離される。
- 画面の要素は、旧版から引き継いだID・クラス（`#page-*`, `.page.active`, `#toast`, `.show` など）と、ロール/テキストで取得する。
- 並列実行: ローカル4 / CI 2 ワーカー。CIでは失敗時に1回リトライ。
- アサーション方針: 旧v1.1の方針を継続（`class` の完全一致ではなく、CSSセレクタの存在確認や `toHaveClass(/active/)` を使う）。

### 旧TCから変更・廃止した点

| 旧TC | 扱い | 理由 |
|---|---|---|
| localStorageの初期化を前提にしたセットアップ | 廃止 | 新しいユーザー作成 + ログイン注入に置き換え |
| 実在の本番URLに対する実行 | 廃止 | ローカルSupabaseに対して実行 |
| 画面遷移後の固定待ち（sleep） | 廃止 | ロケーターの自動待機に統一 |

## 5. テストの追加・変更ルール

- 新機能を足したら、対応するTCを同じファイルに追加し、ID（`TC-<系統>-<連番>`）をテスト名の先頭に付ける。既存IDは再利用・欠番詰めをしない。
- 仕様変更でテストを変えるときは、この表の「変更・廃止」に理由を残す。
- テストデータは `fixtures.ts` のヘルパーで作る。**アプリの画面を開いた後にDBへ直接データを入れる場合は、再読み込み（または画面復帰イベント）を挟む**（TanStack Queryのキャッシュが古いため。SYNC系で挙動を検証している）。
- 並び替え（ドラッグ）のテストは、3行以上を動かす場合に十分な移動量（220px以上）を使う。
